# Инструкции для Codex

## Назначение и приоритет

Репозиторий содержит backend MVP приложения знакомств, подготавливаемый к продаже как white-label кодовая база. Главный приоритет — воспроизводимый локальный demo-путь: регистрация по телефону, профиль, фото, анкеты, like/pass, взаимный match, чат, текстовые сообщения и демонстрационная подписка.

Перед любой задачей прочитать `docs/PROJECT_CONTEXT.md` и `docs/BASELINE.md`, затем изучить непосредственно связанные файлы. Не считать заявленную возможность рабочей без проверки.

## Границы изменений

- Делать только заявленный объём; не выполнять попутный рефакторинг и не менять публичные API без необходимости.
- Не удалять существующий код дополнительных функций без отдельного указания.
- Не добавлять AI matching, звонки, голосовые сообщения, сложную модерацию, новую admin-панель, Kubernetes, high-load архитектуру, реальные рекуррентные платежи или новые внешние сервисы без отдельной задачи.
- Новое demo-поведение включать только явной переменной окружения и не допускать его в production.
- Не подменять рабочую интеграцию заглушкой, кроме явно обозначенного demo-адаптера.
- Не скрывать исключения пустыми `except`/`catch` и не отключать тесты ради успешного результата.

## Безопасность и внешние сервисы

- Не коммитить `.env`, ключи, токены, пароли, signing-файлы, Firebase credentials или реальные персональные данные.
- В тестах не обращаться к SMSC, Firebase, Yandex Object Storage/S3, DaData, Т-Банку, Telegram или иным реальным внешним сервисам.
- Считать текущий статический телефон/код в auth-контроллере небезопасным production-поведением; не расширять его использование.
- Для seed и demo-данных использовать только вымышленные, идемпотентно создаваемые записи.

## База данных и миграции

- Production-схему изменять только управляемыми миграциями Alembic.
- Не полагаться на `Base.metadata.create_all()` как на механизм миграции и не переименовывать существующие таблицы/колонки без обоснованной необходимости.
- Тесты должны использовать отдельную БД и никогда не использовать URL production/dev из локального `.env` по умолчанию.
- При новой миграции проверить единственность head, `upgrade` с чистой БД и, где возможно, `downgrade`.

## Проверки

- Для дефекта сначала добавить тест, воспроизводящий проблему; для нового поведения — тест контракта.
- Запустить релевантные тесты, затем доступный smoke-набор. Явно перечислить непроведённые проверки и причину.
- Не запускать приложение или импорт с реальными credentials, если это может инициировать внешний вызов.
- Перед завершением проверить `git diff`, `git status` и отсутствие случайных/секретных файлов.

## Текущие команды (baseline)

Поддерживаемая версия Python ещё не зафиксирована проектом: main/socket images используют 3.9, push/admin — 3.11. До нормализации зависимостей использовать Python 3.11 как целевой общий runtime и явно сообщать, если проверка выполнена другой версией.

```text
python -m venv .venv
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

# Запуск из корня с PYTHONPATH, содержащим корень репозитория
cd main_app; python app.py
cd socket_app; python app.py
cd push_app; python app.py
cd admin_app; uvicorn app.main:app --host 0.0.0.0 --port 1027

# Заявленная CI-проверка; тестов и pytest в baseline пока нет
pytest

docker compose config
docker compose up --build
```

На исходном baseline первая установка в созданном Codex `.venv` на Windows/Python 3.12 блокировалась сборкой `pywatchman` без MSVC Build Tools; после установки toolchain повторная установка прошла. Main/socket Dockerfile больше не требуют локального `wheels/`. Docker Desktop доступен по `C:\Program Files\Docker\Docker\resources\bin\docker.exe`, даже если текущий процесс ещё не видит его через `PATH`. Не выводить результат `docker compose config` без редактирования: Compose разворачивает значения секретов из `.env` в консоль.

## Совместимость и отчёт

Если необходимо изменить контракт, до реализации описать причину, затронутые endpoints/Socket.IO events и влияние на Flutter-клиент. В итоговом отчёте указать: выполненное, изменённые файлы, команды проверок и результаты, ручную проверку, ограничения/риски и изменения API, БД, env, Compose и требований к Flutter.
